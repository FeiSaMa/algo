## 〇、一句话总纲

★ **Big-O 只说「量级」不说「常数」；而 TLE 与否常常由常数决定 —— 常数来自内存布局与指令调度。**

```
Big-O  →  会不会 TLE（量级）
内存/调度 →  会不会被卡常数（同一量级内的快慢）
```

★ **决策原则（按本人学习约定）：**
- 默认只用「够快」的写法 —— **过题优先**
- 内存/调度知识用于**选型**（选对容器、选对访问顺序）
- **只在线 TLE 时**才做深度优化（reserve / 展开 / 卡常）

## 一、内存层级与 cache（ACM 版的「为什么」）

### 1.1 层级（越靠上越快越小）

```
寄存器 → L1 → L2 → L3 → 内存
 ~0周期  ~4    ~14   ~50   ~200+ 周期
```

★ **算法题里的所有「快慢常数」，本质都是「数据在不在近处」。**

### 1.2 cache line（64 字节 = 8 个 double / 16 个 int）

★ **CPU 按 64 字节一块搬，不是按单个元素搬。**

| 访问模式 | 想要的 | 实际搬来 | 用上 | 后果 |
|---|---|---|---|---|
| 连续（`v[i]` 递增 i） | 1 个 | 64 字节 | 8 个全用 | 划算 + 可预取 |
| 跳跃（大 stride） | 1 个 | 64 字节 | 只用 1 个 | 巨亏 |

★ **结论：能连续访问就连续访问。**（你这台机 L1d 576 KiB / L2 24 MiB / L3 18 MiB）

### 1.3 二维数组：行优先

```cpp
a[i][j]   // 内存里 a[i*n+j] → 同一行连续，同一列隔 n
```

⚠️ **按列遍历 = 大 stride = 反复 miss cache。**（matmul-opt 的 L0→L1 就是靠改遍历顺序涨了 18 倍）

## 二、C++ 容器的内存布局（选型核心）

### 2.1 一张总表

| 容器 | 底层 | 内存布局 | 查找 | 插入 | 缓存友好度 |
|---|---|---|---|---|---|
| `vector` | 动态数组 | **连续** | O(1) | 尾部均摊 O(1)；中间 O(n) | ★★★★★ |
| `deque` | 分段数组 | **多块连续** | O(1) | 头尾 O(1) | ★★★☆ |
| `list` | 双向链表 | **节点分散** | O(n) | O(1) | ★（几乎最差） |
| `stack`/`queue` | 默认 `deque` 适配 | 同 deque | — | 顶/尾 O(1) | ★★★☆ |
| `unordered_map/set` | 哈希表（桶+链表） | 桶数组 + 分散节点 | 平均 O(1) | 平均 O(1) | ★★ |
| `map`/`set` | 红黑树 | **节点分散** | O(log n) | O(log n) | ★ |

★ **口诀：能用 `vector` 就用 `vector`（连续 = 快）；只在需要特定操作时才换。**

### 2.2 为什么「同为 O(1)」却差很多

| 对比 | 差距来源 |
|---|---|
| `vector[i]` vs `list` 遍历 | 连续 vs 指针跳转（每次跳 = 可能 miss） |
| `unordered_map` vs `map` 查找 | 哈希 O(1) vs 树 O(log n)；但 unordered 节点也分散 |
| `deque` vs `vector` 随机访问 | deque 要算「块号+块内偏移」，多一层 |

## 三、逐个容器的「底层视角」

### 3.1 `vector`：连续 + 扩容

```cpp
vector<int> v;
v.push_back(x);      // 满了 → 申请 2 倍新空间 → 搬全部 → 释放旧的
```

★ **为什么 `push_back` 是「均摊 O(1)」**：偶尔一次 O(n) 搬家，摊到 n 次插入上 = O(1)。
⚠️ **「均摊」≠「每次」**：某一次 `push_back` 可能突然慢（在搬家）。

★ **`reserve(n)` = 提前把容量开够 → 全程不搬家。**（已知要装 n 个元素时用）

```cpp
vector<int> v;
v.reserve(n);        // 一次性开够，杜绝扩容搬家
```

### 3.2 `deque`：分段连续

```
[块0][块1][块2]...   每块是一段连续内存，块之间用指针数组串起来
```

★ **头尾插入/删除 O(1)，但随机访问 `d[i]` 要「算块号 + 块内偏移」** → 比 vector 多一层计算。
★ **用途：需要「两头进出」时**（→ 239 单调队列用 deque 的原因）。

### 3.3 `stack` / `queue`：适配器

★ **不是独立容器，而是「用别的容器包装出受限接口」**（默认底层是 `deque`）：

```cpp
stack<int> st;       // 默认 stack<int, deque<int>>
queue<int> q;        // 默认 queue<int, deque<int>>
```

- `stack`：只能顶进顶出（LIFO）
- `queue`：只能尾进头出（FIFO）
- ⚠️ **没有 `clear()`、不能遍历、不能随机访问**（故意的——限制接口防误用）

### 3.4 `unordered_map/set`：桶 + 链表

★ **底层是一个数组（桶），每个桶挂一条链表；冲突就挂到同一条链上。**

```
key → hash → % 桶数 → 定位桶 → 链表上逐个比较
```

- **负载因子** = 元素数 / 桶数；默认 `max_load_factor = 1.0`
- **超过阈值 → rehash**：扩桶 + **所有元素重算位置搬家**（O(n)）
- ⚠️ **最坏情况**：全撞一个桶 → 退化成 O(n)（哈希碰撞攻击）
- ★ **`reserve(n)` 预开桶 → 杜绝 rehash**（和 vector 的 reserve 同理）

⚠️ **`mp[key]` 键不存在时会「自动创建 0」**（判断存在请用 `count`/`find`）—— 见 `第0层-基础工具/哈希表-专题笔记.md`。

### 3.5 `map`/`set`：红黑树

★ **有序**（按键升序），**稳定 O(log n)**，但**节点分散在堆上** → cache 不友好、常数大。

| | `unordered_map` | `map` |
|---|---|---|
| 底层 | 哈希表 | 红黑树 |
| 查找 | 平均 O(1)（最坏 O(n)） | 稳定 O(log n) |
| 有序 | ❌ | ✅ |
| 常数 | 通常更小 | 更大 |
| 怕被卡 | ⚠️ 是（碰撞攻击） | ❌ 不怕 |

★ **ACM 选型**：只要「查在不在 / 值→位置」→ `unordered_*`；需要**有序遍历/前驱后继**或**怕被 hack** → `map`/`set`。

## 四、字符串的内存与拷贝（⚠️ 高频坑）

### 4.1 `string` 的 += vs 拼接

```cpp
s += c;           // ✅ 原地追加（可能扩容），均摊 O(1)
s = s + c;        // ❌ 生成新串 + 拷贝整个 s + 再赋值 → O(n) 每次！
```

★ **循环里拼字符串，永远用 `+=`。**

### 4.2 `substr` / 传参：会拷贝

```cpp
s.substr(i, len);          // 生成一个新的 string（拷贝 len 个字符）
void f(string s);          // 传值 → 拷贝整个串！
void f(const string& s);   // ✅ 传引用，不拷贝
```

⚠️ **题目里若要比较/匹配子串，`substr` 每次 O(len) 拷贝** —— 能用下标+引用就别拷贝。

### 4.3 SSO（小字符串优化）

★ **短 string（libstdc++ ≤ 15 字节）直接存在栈上的对象里，不另分配堆内存** → 小串的拷贝相对便宜，但仍非零。

## 五、调度与分支（进阶，遇到再深入）

### 5.1 分支预测

```cpp
// 有序数组上求和，比完全随机的同规模数组快 —— 分支预测命中率高
```

★ **if 的分支如果可预测（如绝大多数走同一分支），飞快；随机跳转则慢。** 这就是「有序数组比无序快」的底层原因。

### 5.2 递归 vs 迭代的栈帧

- 每次函数调用 = 一次**压栈**（返回地址、局部变量、保存寄存器）→ 有开销
- 深递归还会**爆栈**（栈空间有限，默认几 MB）
- ★ **BFS/DFS 深搜时，递归可能 TLE 或爆栈 → 改写迭代 + 显式栈**

### 5.3 小函数的内联

★ **`O2/O3` 下，小函数（如 `bool isMatched(...)`）会被内联** → 调用开销消失。所以别怕拆小函数（可读性 > 微优化）。

### 5.4 LeetCode 的编译选项

★ LeetCode 用 **`-O2`**（开了优化）→ 你写的循环**可能被自动向量化/展开**。所以「看汇编猜性能」在 LC 上不总准（环境不可控）。

## 六、ACM 实战：容器选型决策表

| 需求 | 选 | 理由 |
|---|---|---|
| 动态数组、随机访问 | `vector` | 连续、cache 最友好 |
| 已知元素个数 | `vector` + `reserve(n)` | 杜绝扩容 |
| 只在一端进出（LIFO） | `stack`（或 `vector`） | `vector` 更快但接口不明确 |
| 两端进出（FIFO/滑窗） | `deque` | 头尾 O(1) |
| 查存在 / 计数 | `unordered_set` / `unordered_map` | 平均 O(1) |
| 值→位置/答案 | `unordered_map` | 同上 |
| 需要有序 / 防 hack | `map` / `set` | 稳定 O(log n) |
| 频繁中间插入删除 | `list`（谨慎） | 但 cache 极差，通常用 `vector` 更划算 |

★ **默认思维：先想「能不能用 vector / 连续存储」，再考虑别的。**

## 七、一句话总结

> ★ **Big-O 决定会不会 TLE，内存布局决定同一量级内的快慢。**
>
> **三条最实用的：**
> 1. **能连续就连续**（cache line 64 字节，连续全用上，跳跃浪费 7/8）
> 2. **能 `reserve` 就 `reserve`**（vector / unordered_*，杜绝搬家）
> 3. **能 `vector` 就 `vector`**（连续 = 快；只在需要特定操作时才换容器）
>
> **但不是让你提前优化 —— 默认选对型即可，深度卡常只在线 TLE 时做。**
